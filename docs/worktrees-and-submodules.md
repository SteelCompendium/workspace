# Worktrees & Submodules — Cheatsheet

The workspace is a **superproject**: it pins exact commits of the authored
sub-repos (`steel-etl`, `v2`, `steelCompendium.github.io`, `data-sdk-npm`,
`data-gen`, `compendium`, `draw-steel-elements`, `statblock-adapter-gl-pages`)
as **submodules**. `data/` is *not* pinned — it is regenerated by the pipeline.

## Mental model

- A **submodule** = the superproject remembers "this sub-repo is at commit X."
- A **worktree** = the same repo checked out in another folder on another
  branch, sharing one history. We use one worktree per parallel agent/task.

## First-time setup on a machine

    git clone --recurse-submodules git@github.com:SteelCompendium/workspace.git
    cd workspace && just bootstrap   # idempotent catch-up

## Everyday commands

| Goal | Command |
|---|---|
| Sync this checkout to origin | `just sync` |
| New isolated env for a task | `just wt-new <name>` |
| What has my env changed? | `just wt-status <name>` |
| Land env work (PUBLISHES) | `just wt-finish <name>` |
| Remove an env | `just wt-rm <name>` |

Environments live in `../worktrees/<name>/` (sibling of `workspace/`).
`wt-new` references the main checkout's object stores, so a new env spins up in
seconds and works offline (no re-clone from GitHub).

## The two-commit rule (read this twice)

Changing a submodule is **two commits**:

1. Commit *inside* the submodule (e.g. in `worktrees/foo/v2`).
2. Commit in the **superproject** recording the new pointer (`git add v2`).

If you skip step 2, the superproject still points at the old commit and your
change "disappears" on other machines. `just wt-status` and lazygit's
Submodules panel show pending bumps so you notice. (`wt-rm` refuses to delete an
env with an uncommitted pointer bump — that is the guard catching step 2.)

## Detached HEAD is normal (when consuming)

After `just sync` / `git submodule update`, submodules sit in **detached HEAD**
at the pinned commit. That is correct for *using* a version. Only **edit** in an
env created by `wt-new` (which branches every submodule for you, named after the
env) so commits are never lost.

## Landing work — what `wt-finish` does

Worktree submodules are *independent clones*, so origin is the sync point.
`just wt-finish <name>`:

1. For each submodule with commits on branch `<name>`, pushes them onto the
   submodule's tracked branch on origin (`main`, or `v3` for `data-sdk-npm` /
   `data-gen`).
2. Switches the **main** checkout to `main`, merges the superproject `<name>`
   branch, runs `submodule update` (fetching the just-pushed commits), and
   pushes `main`.

It **publishes** — it writes to multiple origin `main`s. Requires the env *and*
the main checkout to be clean. Run it from the main checkout. If a tracked
branch moved underneath you, the submodule push is rejected (safe) and you
reconcile manually.

> Deploy/publish of the **site** still happens only via `just deploy` on `main`
> (see below). `wt-finish` lands source; `deploy` regenerates + publishes.

## After `main` moved while you were working

    just sync                       # in the main checkout
    # in your env, rebase the env branch onto the new main as needed

## Driving it from lazygit

- **Worktrees panel** (`w`): create/switch/remove worktrees visually.
- **Submodules panel**: `enter` a submodule to operate inside it; the
  superproject view shows a pending pointer change to stage (the two-commit
  rule, made visible).

## Deploy

Deploy/publish happens **only on `main`**, serialized, from the main checkout —
never from an env. `just deploy` regenerates, pushes generated content into the
`v2`/org-site submodules, and bumps their pointers. Feature branches may run
`gen` to verify but write only to their own scratch `data/` and never publish.

## Gotchas

- `data/` is scratch: never `git add` it in the workspace (it is gitignored).
- `wt-rm` refuses to delete an env with uncommitted work (including an
  uncommitted pointer bump) — commit or discard first.
- Single remote: `origin` → SteelCompendium. There is no `fork` remote.
- Submodule git-dirs are absorbed under `.git/modules/<name>`. If you ever add a
  new submodule with an embedded `.git`, run `git submodule absorbgitdirs` so
  `wt-new`'s object-sharing works.
- Run Go/just/mkdocs through devbox: `eval "$(devbox shellenv)"` first, or
  `devbox run -- <cmd>` (note `devbox run --` resets cwd to the workspace root).
