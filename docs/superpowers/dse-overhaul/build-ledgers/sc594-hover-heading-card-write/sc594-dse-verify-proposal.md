## 2. New bullet "Hover card writes (SC-594)" (under "Block edit form Save and embeds (SC-556)", after the SC-584 bullets)

> - **Hover card writes (SC-594).** A card's + / - in a hover preview (or an embed) of PART of a note is a write whose pin is in the part's coordinates. `rebaseCardPin` (not the forms' `rebasePin`) places it: the part IS the note; else the LINK (the embed's `src`, or for a hover preview the link of Obsidian's `hover-link` workspace event for THAT popover, `src/framework/host/hoverLinks.ts`) checked by `cardLinkLine`; else this host's own last write when it is of the known body; else the write is refused with today's dropped-write Notice. It never searches the note for the part's text (`searchedPinLine`) or for the body. No event, no link, a refusal.
>   - **What `cardLinkLine` checks (r4).** The link must resolve to THIS note. EVERY line of the part (trailing blanks dropped) must equal the note from where the link starts; the card's fence must hold the known body; a `^id` link needs its `^id` marker after the block and, while the known body occurs twice, exactly ONE `^id` marker line in the text. A HEADING link is placed from the note TEXT, not from the metadata cache alone (`headingNames.ts`: `atxHeadings`, `normalizeHeadingName`): a heading hover's part is the heading's BODY, so the line it hangs from (`start`, from the cache) must be, in the text, an ATX heading line of the link's name (a cache that lags a moved / pasted / deleted section points at another heading or a blank line: refused), and while the known body occurs twice the text must hold exactly ONE heading of that name (count from the text, outside fences; the cache's count is not used).
>   - **The hover-link log.** Registered once at load (`registerHoverLinks`, from `registerFrameworkElements`, so `onload`; a listener registered when the first card is built missed that hover's own event). The link is BOUND to a popover once: at the first lookup for that popover element, or at the arrival of the NEXT `hover-link` event (any link), whichever comes first (a null result is bound too). Previews already open when the listener registers are bound to NO link. Measured (r2, 1.15.1): a card is built and mounted while its element is still DETACHED (`closest('.hover-popover')` is null at construct and at `setMountedBody`; the card is attached 10-14 ms after the popover), so a card cannot ask which popover it is in until a click; a pass-over of another link on the same parent (event at ~650 ms, its popover never opened, `hoverParent.hoverPopover` still X's) used to become "the newest event of X's popover" and wrote the identical counter under Y's heading. The bind-at-next-event step closes that. `hoverParent.hoverPopover` is set only when the popover is shown (r3 read of `app.js`), so at a second link's event it is still the SHOWN popover: the next-event bind binds X to X.
>   - **The DOM cross-check (r4, `popoverShows`).** The bound link must be what the popover's own DOM shows (measured: `.markdown-embed[data-type=heading]` with the first `[data-heading]` = the heading name; `data-type=block`; a whole-note hover has no `data-type`). Otherwise `hoverLinkOf` returns null and the write is refused. It closes the residual r2 named (another link's event before the popover exists) for HEADING links, and a whole-note link bound to a heading or block preview. It does NOT tell two BLOCK previews apart (no id is rendered: a `^a` preview bound to `^b`'s link still passes `data-type=block`); a real pointer cannot produce that in 1.15.1 (r3), jest can.
>   - **Heading hover shape.** A heading hover's section is the heading's body (no heading line, `lineStart` 1); a block hover's is the block's own lines (`lineStart` 0); a whole-note hover's is the whole note (`isWhole`). A jest model of a heading hover must use the body (`part(SUB, 2)` with the heading line is the shape of `![[note#H]]` EMBEDS only) AND give the popover DOM the host checks (`hoverEl(link)` in `reading-mode-host-pin.test.ts` and `popoverEl(link)` in `reading-mode-host-hover-card.test.ts` note the `hover-link` record and draw `data-type` / `data-heading`). A jest cache mock must lag an outside edit by passing the OLD note's lines to `cacheFor` (`hovered(..., cachedNote)`); a cache mock that follows the note hides the whole heading-hover hazard class.
>   - **The card guard in `takePin` is load-bearing.** The r7 guard for cards (`if (embedded)` -> `pinFromLastWrite()` for a window that is not the block's own plain fence) is killed by J19: a second + after an outside edit put the first + back, in a stale two-counter callout window, writes the SIBLING counter without it.
>   - **The 17-44 ms window (only for edits that change the preview's text).** After an outside write lands (Sync, another app) the preview redraws its card 17-44 ms later (measured n=10 RV/LP) when the part's TEXT changed; a scripted `.click()` on + in the SAME page task as `await vault.process(...)` lands before that redraw. G-S92 (g) (block hover), (h) (heading hover, counter edited) and (j) (heading hover, the identical `## Other` section moved ABOVE `## Tracker`: the metadata cache still has the old lines for ~6-45 ms) drive exactly that: the note must stay as the edit left it, one dropped-write Notice. A real mouse click sent after the edit cannot land inside it. Look up the + button of the OLD card AFTER the edit resolved, inside the same task. An edit that leaves the part's text unchanged (the hovered one of two identical `## Tracker` sections deleted, two heading names swapped) does NOT redraw the preview (r5, measured over 1.5 s), so there is no window to close: see "Known limit (SC-607)" below.
>   - **G-S92** (its own part 6; in SCENARIOS order after G-S91, before G-S56; about 103 s alone as part 6 with the build and start-up): (a) `[[long#Tracker]]` Reading view, (b) Live Preview, (c) short note, (d) `[[note#^id]]` with an identical block carrying another id, (e) a second real + 450 ms after the first (A = 7), (f) a callout under the heading with an identical callout elsewhere; (g) (h) (j) the scripted-click trials above; (i) whole-note hover, an identical block added above from outside (the hovered block is written, not the added one); (k) hover `[[#Tracker]]`, then `[[#Other]]` with the first preview open, a real + in the second preview lands in ITS counter (the T1 shape; green on the r2 bundle too: a regression guard for the bind). One note per trial (a card Notice is rate limited per note). Red on the e0e49d4d bundle: (a)-(i); (j) is red on the 0bf5989d bundle (wrote the counter under the old line, no Notice).
>   - **Still refused (Notice, nothing written) — exactly:** (1) a counter in a list item or a footnote (SC-461); (2) a counter edited from outside just before the click (the preview still shows its old value), or a hovered section moved, pasted over or removed from outside just before the click while the metadata cache has not caught up (the part no longer equals the note where the link starts, or the hanging heading line is not that heading in the text, or the heading name occurs twice in the text while the body occurs twice); (3) a hover with no `hover-link` record, one already open when the plugin loaded, or (heading links) one whose DOM shows another heading than the bound link names; (4) a link that names two places (two headings of that name, two `^id` lines) while the body also occurs twice; (5) a HEADING hover whose heading is written with an underline (setext) or whose text on the line differs from the link's name after trim / whitespace collapse / lower case (formatting, links, a colon: `## Tracker: one` linked as `[[note#Tracker one]]`; safe, base refused it too); (6) a block link whose `^id` marker is not directly after the block (a lagging cache points at another block); (7) a whole-note hover whose counter was edited from outside. Forms (`pinPosition` -> `rebasePin`) and null-pin paths are NOT covered (SC-596). Unchanged: an unwritable list shape ("can't tell where").
>   - **Known limit (SC-607; behaviour as before SC-594, NOT refused).** With a FRESH metadata cache a + in a preview that is still open follows what the link names NOW, and a preview whose part text did not change is never redrawn. So: (a) the hovered one of two identical `## Tracker` sections deleted from outside while the preview stays open: the click is saved in the other `## Tracker` counter, no Notice; (b) two heading names swapped from outside while the preview stays open: the click is saved in the counter now under the link's heading. Both also write on b5d18f79. The fix (pin the card to the note as drawn at mount, map it at click) is SC-607 (Backlog); do not write a phase that expects a refusal there.
