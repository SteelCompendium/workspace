## Ticket text (verbatim, the spec)

> Hover over a link to a note that holds a counter, then press the Edit pencil in the preview. The edit form opens. The first mouse click anywhere inside the form closes both the preview and the form. Anything already typed into the form is lost.
>
> The form stays open while the pointer moves into it and rests there. It is the click that closes it. Using only the keyboard (type, then one click on Save) works.
>
> This happens in Reading view and Live Preview, and it happened before SC-584 too.

Agent notes (verbatim): measured by the SC-584 r2 reviewer with a real CDP mouse path (`Input.dispatchMouseEvent`) in Obsidian 1.15.1, on dse develop eeed5182 and on the SC-584 branch (525115b0). RV: press at 6583 ms with the form open; by release + 120 ms both the popover and the form were gone. LP the same. "Most likely Obsidian's hover popover treats a mousedown outside its own element as "dismiss", and the form closes with its view (SC-552: a form is kept open only while its note is shown)."
Report: `docs/superpowers/dse-overhaul/build-ledgers/sc584-embed-form-save-refusals/sc584-r2-review-report.md` (F2); probe logs `sc584-r2-probe-obsidian-head-f2.log`, `sc584-r2-probe-obsidian-base-f2-f3.log` in the same dir.

Implemented once in `DseModal` / `managedModal.ts` so it covers every DSE modal opened from a preview (r1 §5 table). No Scott decision: the preview staying visible behind the form until the next outside click is Obsidian's own behaviour for a preview the user has clicked into; design B (preview closes, form survives) fixes only the form and loses the preview. Offer B in the land-ready comment as the alternative only.
