## MED

### MED-1 — "Log an action…" logs a hidden duplicate entry once everyone has acted in the round in play

- **Where:** `src/elements/montage/view.ts:204`
  `const hero = nextHeroToAct(model) ?? model.participants?.[0]?.name;`
  The bar button then opens `{kind:'new', hero, round: current_round}`.
- **Failure scenario (probed, jest in the real pipeline):** mid fixture (5 heroes, rounds 1–2 fully logged, `current_round: 3`, 5/6 successes).
  1. Click **Back to round 2**, then **Log an action…**. The button is enabled.
  2. The sheet opens titled "Kira · round 2", with the sub-line "the round in play" and Success pre-selected. Press Log.
  3. The written YAML has 11 entries, including two `{hero: Kira, round: 2}` entries, and `successes: 6 / 6`. The verdict flips to **Total Success**.
  4. On the board, the Kira round-2 cell still shows the original Alertness success: `entriesForHero` keeps the first entry for each round, so the new one is never drawn. Kira's row tally still reads "2 successes".
  5. The only visible trace is the verdict change. The duplicate can't be reached through the UI except by Undo, and only while it is the most recent entry.
- **Also reachable without Back:** any round in which every hero has already logged (e.g. via the quick trio), before End round. Probe P-A0: button enabled, Log enabled.
- **Why it matters now:**
  - The fallback predates SC-334. Before SC-334, though, the sheet's Round/Hero chips at least let a Director steer away. R-1 removed them, so nothing in the sheet can stop the write.
  - R-4's Back button lands in a completed round, which is exactly this state.
  - `docs/gm-trackers.md` (new text) says the button "opens the same form for the next hero who hasn't acted yet this round", which is false in this state.
- **Prescribed fix:**
  1. When `nextHeroToAct(model)` is `undefined`, render **Log an action…** real-disabled and drop the `participants[0]` fallback. The existing `disabled || !hero` path already handles this shape.
  2. Defense in depth: in `commitNewEntry` (view.ts), or in `LogActionModal.refreshValidity` for new mode, refuse a new entry whose `(hero, round)` already has an entry.
  3. Add a test: mid → Back to round 2 → `Log an action…` is disabled. Optionally assert that no path writes a second `(hero, round)` entry.

## LOW

### LOW-1 — "hero actions left" overcounts after Back when the round just left has entries

- **Where:** `src/elements/montage/OutcomeBandView.ts:33-35`
  `actionsLeft = roundsLeft * party - actionsThisRound`, which only subtracts entries in `current_round`.
- **Failure scenario (probed):** 2 heroes, 3 rounds, rounds 1–2 full, Kira logged in round 3. The stat reads "1 hero actions left", which is correct. After **Back to round 2** it reads "**2** hero actions left". The truth is still 1 (only Bram's round-3 slot is open).
- The brink alert uses the same number (`toTotal <= actionsLeft`), so it can fire when the montage cannot actually reach the success limit in time.
- **Prescribed fix:** count the open `(hero, round)` slots for rounds `current_round..rounds`: `roundsLeft * party` minus the deduped entries with `current_round <= round <= rounds` whose hero is in the roster. Add one test for the post-Back case.

### LOW-2 — light-theme failure fill is a white-sheened gradient, not the "solid red chip" R-5 describes

- **Where:** `styles-source.css:4686-4689`, `background: var(--dse-sheen), var(--dse-danger)`.
- **Details:**
  - Light `--dse-sheen` (`styles-source.css:13149`) is `linear-gradient(rgba(255,255,255,.9), rgba(0,0,0,.04))`.
  - This is the only place in the sheet where the sheen sits over a saturated fill. Every other use is over neutral ground, and the kit deliberately excludes accent/danger buttons from it (`styles-source.css:10470-10476`).
  - Result: in light theme the chip is pink at the top and red at the bottom (see `tracks-light.png`). The success slot is a matte metal gradient, so the "same filled-chip material" claim in the rule's comment holds in dark only.
- **Contrast:** acceptable. The red border (#bb2d1f) is about 5:1 against the track ground, and filled vs empty is obvious in both themes, so this is a design-fidelity note, not an accessibility failure. Dark theme is fine.
- **Prescribed fix (owner's call):** either override in light (`body.theme-light & { background: var(--dse-danger); }`, keeping the chip bevel), or keep it and correct the comment. Print is untouched either way; freeze stays 260/260.
