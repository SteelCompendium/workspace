## 2. The task

Ticket scope, verbatim from the ledger (Scott, 2026-10-17):

> 1. **A `gif` entry shape in `docs-manifest.mjs`**, alongside the existing `browser` /
>    `obsidian` shapes: an output filename plus a scripted interaction (a sequence of steps —
>    click this control, type this, wait for the write, hover that — with a capture after
>    each). `npm run docs-shots` runs the script, captures the frames, and encodes the GIF.
>    Same provenance rule as the PNGs: an image that cannot be regenerated by a command does
>    not belong in `docs/Media/`.
> 2. **Capture path.** Use whichever camera the element needs: the browser harness (Chromium,
>    deterministic, no display) for elements whose interactions are pure card interactions;
>    real Obsidian on a private Xvfb (`obsidian-camera.mjs` machinery) for anything that needs
>    the block write lifecycle, modals, the sidebar, or Live Preview. GIF encoding from PNG
>    frames with whatever is already in the toolchain or a small, pinned dependency — decide
>    and record in the ticket.
> 3. **One GIF per element**, covering its primary interaction. […] each at steel-dark […]
>    party award, surges, any other interactive element in `docs/` — enumerate from the
>    element registry in the first round and add to this list; static-only elements
>    (statblock, ability card) get no GIF.
> 5. **Determinism and gates.** Frames must be stable across two runs (same frame count, same
>    key frames) or the capture is useless as a regeneration target. The `shots` / freeze /
>    parity gates must not move — `docs-shots` writes only to `docs/Media/`, never to
>    `visual-harness/shots/`. Keep file sizes sane (target under ~1 MB each; frame rate and
>    palette are the levers).
