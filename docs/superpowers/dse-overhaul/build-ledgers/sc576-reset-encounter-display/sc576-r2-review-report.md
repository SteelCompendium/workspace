## Findings

### MEDIUM-1 — the re-parse throw fallback shows the SC-576 screen again, silently
`src/elements/initiative/view.ts:191-198`. `fresh = this.model` on a throw hands `update()` the un-normalised reset model. That is the exact model the bug painted from.
- **Scenario:** a tracker with `statblock: "Orc Warrior"` is open. The statblock note is renamed, deleted or re-synced into a block without `ds-*`. The user presses Reset → Yes. The write lands. `resolveInitiativeRefs` throws "Failed to resolve creature statblock reference…". The tracker repaints with no enemy cells and every hero at `0/<max>` with a DYING chip. There is no Notice; the only trace is a console.error. A reload would show the error card. This fallback shows a wrong live tracker instead.
- **Probe (jsdom, P4):** REFS fixture, `Bestiary/Orc Warrior.md` replaced with plain text after mount, then Reset. Measured: cells 10 → **0**, hero texts **`0/80`, `0/90`**, **8** `[data-state="dying"]` nodes, 1 write, 0 Notices, 1 console.error. Record: `probe-out/head.json` key `P4`.
- **Prescribed fix (owner's pick):** (a) never paint the un-normalised model. On a throw, re-parse a structured clone of the in-memory reset model with `parseModel` only, with no ref resolution. The merged `name`/`max_stamina` are still on it from the first load, so `parse` materialises the instances and the hero stamina. Add a `Notice` that names the failure. Caveat: the clone's SC-485 absent-key records would treat merged keys as authored, so a later write could write merged `name`/`max_stamina` out. That is acceptable only in this failure path; say so in a comment. Or (b) do what a reload does and render the pipeline's error card (`renderErrorCard`) with the thrown error. Either way, pin it with a jsdom test shaped like P4.
- Not a regression: base showed this screen on every Reset. It does mean the fix's own comment ("keep the reset model on screen rather than blanking the tracker") describes the bug screen as the safe choice.

### MEDIUM-2 — e2e `[INIT-X05]`/`[INIT-X06]` do not prove the tracker was rebuilt
`e2e/specs/initiative/reset-encounter.e2e.ts:81-96`. In `Initiative/rich.md`, the Ogres are already at 60/60 and Alice at 30/30 before Reset. Both assertions therefore hold for any implementation that writes the note and never repaints.
- **Mutation probe:** replaced `await this.update(fresh);` with a no-op (`view.ts:198`) in the probe worktree. Result: e2e `INIT-X01 ok, INIT-X05 ok, INIT-X06 ok` (`probe-out/e2e-m2-norebuild.log`), even though the old pre-Reset DOM is never replaced. That is inferred from the code path, not screenshotted; in jsdom the same mutation leaves `Round 3` on screen. The jsdom tests do catch it: `[X01]` reads `Round 3`, `[X05]` reads `-4/30` and `5/12 (4)` (`probe-out/matrix-m2-norebuild.log`).
- Against the ORIGINAL bug both e2e tests are real. With the fix reverted they fail: INIT-X05 with "Index out of bounds … returned only 0 elements", INIT-X06 with `Expected "30/30" Received "0/30"` (`probe-out/e2e-m1-revert.log`). So they are not vacuous. They are weak, in exactly the async/echo path that only real Obsidian exercises.
- **Prescribed fix:** in INIT-X05 or X06, also assert something Reset changes on screen. For example, `.dse-init__round-value` reads `Round 1`, `.dse-init__malice-value` reads `Malice: 0`, and Bruno's `init.hero.turn` has `aria-pressed="false"`. Or point them at a pre-damaged fixture (the probe spec `[PRB576-01]` does the former and passes on the fix head).

### LOW-1 — a click in the await window is silently lost (new window; base had none)
`view.ts:186-198`. The write goes out first. Then the view `await`s `resolveInitiativeRefs`, which reads the vault for every `statblock:` ref. During that await the old, pre-reset DOM is still live and its handlers still mutate the old model. `update(fresh)` then swaps `this.model`, and the debounced write serialises `fresh`. Base rebuilt synchronously (`onMount` is sync), so it had no window.
- **Probe (P5):** gated `refs.resolveBarePath`. While it was held, clicked the hero turn toggle and a roster cell on the still-live old DOM. Neither threw, and both persisted. After release: 2 writes, byte-identical. `has_taken_turn` and `selectedInstanceKey` were absent from the last write, and the turn toggle shows `aria-pressed="false"`. The user's clicks were dropped with no error.
- For ref-free trackers the window is microtasks; for ref-bearing trackers it is the vault-read time (ms). Hard to hit by hand.
- **Prescribed fix (cheap):** mark the root inert during the await (`this.rootEl.inert = true` / `data-dse-busy`, cleared in a `finally`). Or skip the async resolve when the model has no `statblock` strings. Or, structurally, re-apply the merged fields from the in-memory model instead of re-resolving, which also removes MEDIUM-1's throw path.

### LOW-2 — stale doc comment on `rebuildAndPersist`
`view.ts:162`: "The one whole-model change path (Reset Round / Reset Encounter / squad-pool edits…)". Reset Encounter no longer goes through it. The file header (`:43-47`) was updated; this doc comment was not. **Fix:** drop "Reset Encounter" there and point to `rebuildFromWrittenReset`.
